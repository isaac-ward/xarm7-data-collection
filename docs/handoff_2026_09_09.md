## What this is

Xbox-controller teleoperation and world-model data collection for **Swoosh's RIGHT
xArm 7 only**. The left arm (192.168.1.219) is deliberately absent.

The deliverable is a dataset good enough to train a video world model with correct
action conditioning. Isaac gets **one shot** at the collection campaign, so almost
every design decision here trades convenience for "a mistake is visible rather than
silent".

## Start here: three gates

All three are one button each in the dashboard's **sanity** box, bottom left.

1. **Verify 45° frame** (red button). `swoosh-collect` **refuses to start** until this
   passes. It jogs the EE 20 mm along world +X, +Y, +Z; expect **forward, left, up**.
   Saves its result, so it is a one-time thing per matrix.
2. **Check arm.** Asserts the controller's **world offset is zero** (see traps below).
3. **Name cameras.** Nothing records until all four USB ports are labelled.

Then, after one real run: **cmd→measured lag**, **camera latency**, **FK check**,
**workspace reach**.

### Practical order at the robot

```bash
docker compose build
docker compose run --rm cameras                       # name the four cameras
SANITY_ARGS="--home --verify-frame" docker compose run --rm sanity
docker compose run --rm shell -c 'swoosh-campaign new "test"'
CAMPAIGN=test docker compose run --rm collect         # A, wiggle it, B
swoosh-validate --campaign test
```

## Testing with no hardware

```bash
swoosh-collect --campaign test --simulate
```

`SimulatedArm` / `SimulatedPad` / `SimulatedCameraRig` implement the same interfaces
and slot in, so this drives the **real** loop, recorder, dashboard and export — not a
mock of them. The simulated cameras write real mp4s and timestamp files, so a
simulated A-to-B episode is a genuine run folder that summarises, plays back,
validates and exports. Use it to shake out UI work before the arm is powered.

The physics is deliberately crude (first-order lag, joints are smooth wobble, not an
IK solution). It is not a robot model.

## Traps — please read before changing anything

**Don't switch to `set_world_offset`.** It is tempting: the SDK has it, and it would
move the 45-degree rotation into the controller. It was investigated and rejected on
purpose — reasoning is in `frames.py`. The frame would then live in controller flash:
invisible to the dataset, persistent across reboots, changeable from xArm Studio, and
global to every other tool on that arm. That is exactly the class of unrecorded frame
that made `lego_assemblies` unusable. We keep the matrix because it is written into
every run's provenance.

Corollary: the code **asserts the controller's own world offset is zero**, because a
leftover one would stack on ours and rotate everything twice, silently.

**Don't use `yaml.safe_dump` on `conf/collect.yaml`.** Use `config.set_value()`, which
round-trips through ruamel. An earlier version erased all 77 comment lines, and that
file is where most of this project's hard-won knowledge lives.

**`collision_sensitivity` is 0** — matching manipulation-mono, because the controller's
payload model does not know the gripper's mass and even sensitivity 1 spuriously trips
error 31. **Real collisions are not caught.** Clear the workspace before any jog.

**The xArm7 DH table is unverified.** It comes from UFACTORY's published values and
drives only the **pose** of the 3D arm. The wireframe box, target sphere and gripper
animation do not depend on it. The FK-check button settles it: FK and the controller's
reported TCP should differ by roughly the TCP offset, since our FK stops at the flange.

**The SDK has no non-blocking gripper call.** `set_gripper_position` does a modbus
transaction (5–15 ms); `wait=False` only means "don't wait for the fingers". Hence the
worker thread in `arm.py`. Don't move it back onto the control thread — it would slow
the loop *only while squeezing*, silently changing what `action` means.

**`bash -lc` breaks the container.** A login shell re-initialises PATH from
`/etc/profile` and discards the venv. Fixed with an `/etc/profile.d` drop-in; don't
remove it. (`evdev` also needs `build-essential` + `linux-libc-dev` to compile.)

## The prior disaster this is all defending against

The previous dataset, `swoosh-data/lego_assemblies`, had four failures. Each has a
specific guard here; if you weaken one, know what you are giving up.

| lego failure | guard now |
|---|---|
| `action` was raw VR controller pose in an unrecorded per-session frame (R² 0.0298 vs 0.0002 shuffled — noise) | `action` is the Xbox input; commanded pose and the literal SDK arguments ship as separate columns; the frame matrix is in every run's provenance |
| raw log and exported episode had **no shared time origin** (0–1 s, varying per episode) → every action ~24 frames from the observation it caused | every stream, cameras included, is stamped against one `t_loop0`; the exporter **refuses** a run whose stream starts differ by >5 s; `tests/test_roundtrip.py` has a regression test for exactly this |
| `observation.state` silently sample-and-held at ~9 Hz despite being labelled 30 Hz (70% of rows byte-identical) | `swoosh-validate` measures held-value fraction per stream; a `tick` stream records measured loop dt |
| a mask threw away 46% of frames to handle 0.8% bad ones | no mask; instead a `flags` column (clamped / servo_code / arm_error / pad_connected) so a consumer decides |

**The one hard rule:** the raw JSONL streams are authoritative, the LeRobot export is
derived. If a framing decision turns out wrong, re-derive from `raw/` — do not
re-collect.

## Things that are known-imperfect

- The 3D arm's pose depends on the unverified DH table (above).
- `summarize` runs as a `nice`'d subprocess and streams frames, but a very long episode
  will still take a while; A is gated while a run is processing.
- The dashboard's camera preview is throttled to 10 fps at 320×240 on purpose, so JPEG
  encoding cannot starve the servo loop. It is not a quality view.
- `swoosh-validate` warns on high workspace-clamping fraction; in simulation this is
  normally 40–60% because the fake sticks push continuously into the walls. On real
  data a high number means the box is too small.
